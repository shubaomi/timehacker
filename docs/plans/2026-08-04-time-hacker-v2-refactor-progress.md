## 4. 当前确认的问题

### 4.1 玩法框架问题

- `src/game/puzzle-scene-catalog.ts` 虽有 100 条 seed，但统一经过 `authoredScene()` 生成相同三物件结构。
- 每关固定由第一个物件负责发现、第二个负责破解、第三个只作装饰。
- `src/components/puzzle-scene.tsx` 把 `drag`、`align`、`rotate`、`trace`、`orbit`、`rub`、`balance`、`assemble` 合并为同一个 `move` 判断。
- 当前移动类行为通常只需超过约 42px，无法表达轨迹、角度、空间关系或拓扑差异。
- CSS 让非当前目标不能接收指针，玩家无法通过试验获得合理反馈。
- 第三个物件是 `aria-hidden` 且不可交互，场景看似丰富但实际只有一个正确入口。
- 错误目标被直接忽略，造成“点击了但没反应”的体验。

### 4.2 测试证明范围问题

- 当前 E2E 会读取内部 `puzzleScene` 答案和 target ID 后执行操作。
- 组件测试可以用键盘 Enter 走过多种机制。
- 这些测试证明数据契约可以完成，不证明玩家能从画面推断答案。
- `docs/puzzle-playtest-review.md` 是开发者启发式检查，不是真正未知答案的玩家盲测。

### 4.3 显示与文案问题

- `src/game/timer.ts` 的 `formatSignedError()` 当前仍使用三位小数。
- 部分 `src/i18n/config.ts` 文案仍包含 `10.000`、实验室和仪式语汇。
- 当前提示被删除得过度，玩家缺少“每关存在作弊方式”的最低认知。
- 当前场景图标过于像可点击按钮，但错误或非当前图标又没有反馈。

### 4.4 控制台报错边界

用户截图中的 `chrome-extension://...`、`Unchecked runtime.lastError` 属于浏览器扩展上下文，不能据此认定 Time Hacker 应用代码报错。后续 E2E 应在干净浏览器上下文中要求应用自身零 console error，同时把扩展报错与应用错误分开记录。

## 6. 下一阶段建议顺序

### 阶段 A：设计审核和冻结

只评审文档，不写代码。

1. 逐关确认“推理依据是否足以支持答案”。
2. 优先审核风险最高的关 02、06、09、12。
3. 确认关 07 的设备倾斜是否保留为可选输入。
4. 确认关 09 的真实切标签是否符合轻量小游戏定位。
5. 确认关 12 的摄像头是否只在终章出现。
6. 为每关按设计稿评分，未达门槛继续修改。
7. 冻结设计稿版本，再创建实现 Goal。

完成标志：本文档的 12 关全部被明确接受，没有“实现时再想”的核心规则。

### 阶段 B：技术方案与最小骨架

1. 新增 `/playtest-v2`，正式首页暂不替换。
2. 设计 V2 状态机和关卡接口。
3. 只实现关 01、02、03，验证新架构不再依赖通用 `move`。
4. 建立正确/错误反馈、提示和计时辅助共用能力。
5. 完成桌面和手机浏览器验收后再实现余下 9 关。

完成标志：前三关的发现和破解在代码层面真实不同，并经过产品负责人试玩。

### 阶段 C：完成 12 关垂直切片

1. 按冻结规则实现关 04–12。
2. 为轨迹、角度、组装、等待、节奏、页面可见性和设备能力编写独立识别器。
3. 自动化测试不得只读取内部答案并按 Enter。
4. 运行 lint、typecheck、unit、component、integration、build、Playwright 和只读数据库检查。
5. 推送 GitHub，但不自动部署。

完成标志：技术验收全部通过，试玩地址可部署，仍明确标记“等待真人验证”。

### 阶段 D：盲测与回改

1. 至少 3 名未读答案的人完成试玩。
2. 记录发现时间、提示使用、失败点、趣味性和成就感。
3. 修改“毫无依据、过于明显、无反馈、跨端不公平”的关卡。
4. 重新测试并由产品负责人决定是否替换首页。

### 阶段 E：扩充到 100 关

按 `12 → 30 → 60 → 100` 批次扩充。每一批都要做重复性审计和玩家抽测，不允许从 12 个模板生成剩余关卡。

## 7. 预计主要文件影响（尚未执行）

后续实现可能涉及：

- 新增 V2 试玩路由和页面组件。
- 新增关卡专用场景组件或混合式关卡注册表。
- 替换当前把多种机制合并为 `move` 的识别逻辑。
- 新增轨迹、角度、空间关系、节奏和等待识别器。
- 更新计时显示统一两位小数。
- 更新双语提示与残留实验室文案。
- 更新组件、单元、集成和 Playwright 测试。
- 视最终数据映射决定是否更新 seed；当前不预设必须迁移 Prisma schema。

设计原则：共享输入基础设施，但允许关卡拥有专用场景控制器。不要为了“所有关卡都来自一个 JSON schema”而牺牲玩法表达。

## 8. 数据与部署注意事项

- 共享数据库意味着本地测试可能影响生产数据，实施时先建立隔离策略。
- `deploy.sh` 当前会执行迁移和 seed；实现前必须确认 seed 不会覆盖真实解锁或成绩。
- 试玩阶段建议以独立路由发布，不改 Nginx 域名映射。
- 服务器仍使用 `PORT=3008`、PM2 `timehacker` 和现有反向代理。
- 不把数据库连接串写入文档、源码或提交。
- 不在设计阶段执行生产部署。

- V2 已实现。

- 12 关已通过真人试玩。
